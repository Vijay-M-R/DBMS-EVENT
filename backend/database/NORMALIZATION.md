# Database Normalization & DBMS Academic Specification

## Freelance Service Marketplace

This document provides a rigorous academic analysis of the relational database design for the Freelance Service Marketplace, demonstrating strict adherence to First Normal Form (1NF), Second Normal Form (2NF), and Third Normal Form (3NF), along with complete mappings for advanced DBMS academic demonstrations.

---

### 1. Normalization Analysis (1NF, 2NF, 3NF)

#### First Normal Form (1NF)
**Requirements:**
1. Each column must contain only atomic (indivisible) values.
2. There are no repeating groups or arrays stored as comma-delimited strings.
3. Every row must be uniquely identifiable by a Primary Key.

**Compliance in our Schema:**
- In `addresses`, composite location data is decomposed into discrete atomic attributes: `address_line`, `city`, `state`, `pincode`, and `landmark`.
- In `availability_slots`, time intervals are split into distinct atomic columns: `slot_date`, `start_time`, and `end_time` rather than combined ranges or multi-slot arrays.
- Every table has a clearly defined synthetic primary key (`user_id`, `customer_id`, `provider_id`, `service_id`, `slot_id`, etc.) using `BIGINT GENERATED BY DEFAULT AS IDENTITY`.

#### Second Normal Form (2NF)
**Requirements:**
1. The table must already satisfy 1NF.
2. All non-prime attributes must be fully functionally dependent on the entire primary key (no partial key dependencies).

**Compliance in our Schema:**
- All 10 tables utilize a single-column primary key (`BIGINT IDENTITY`).
- By relational database theory, if the primary key consists of a single attribute, **partial dependency cannot exist**.
- For tables with composite unique constraints (e.g. `availability_slots (provider_id, slot_date, start_time, end_time)`): Every non-key attribute (`slot_status`, `created_at`, `updated_at`) depends on the complete combination of provider, date, and time. No attribute depends solely on a subset of the candidate key.

#### Third Normal Form (3NF)
**Requirements:**
1. The table must already satisfy 2NF.
2. No transitive dependencies exist: no non-prime attribute depends on another non-prime attribute ($X \rightarrow Y$ and $Y \rightarrow Z$).

**Compliance in our Schema:**
- In `users`, non-key attributes (`full_name`, `email`, `password_hash`, `phone`, `role`, `account_status`) depend directly on `user_id`. There are no transitive dependencies between non-key fields.
- In `services`, the category details (`category_name`, `description`) are NOT embedded inside the `services` table. Instead, a foreign key `category_id` references the normalized `categories` table. If category attributes were stored in `services`, updating a category name would produce update anomalies.
- In `bookings`, provider identity is not duplicated because `service_id` and `slot_id` already establish the provider context. Customer addresses are kept in `addresses` and referenced via customer identity, preventing redundant transitive duplication.
- In `reviews`, provider metrics are NOT stored in the review record; review relates strictly to `booking_id` and `customer_id`. The aggregate rating in `provider_profiles` is an intentional materialized performance aggregate maintained deterministically by an automated database trigger (`trg_update_provider_ratings`).

### 2. Table-by-Table Functional Dependencies & Keys

#### Table 1: `users`
- **Candidate Keys:**
  - $CK_1 = \{\text{user\_id}\}$ (Primary Key)
  - $CK_2 = \{\text{email}\}$
  - $CK_3 = \{\text{phone}\}$
- **Functional Dependencies:**
  - $\text{user\_id} \rightarrow \{\text{full\_name}, \text{email}, \text{password\_hash}, \text{phone}, \text{role}, \text{account\_status}, \text{created\_at}, \text{updated\_at}\}$
  - $\text{email} \rightarrow \{\text{user\_id}, \text{full\_name}, \dots\}$
  - $\text{phone} \rightarrow \{\text{user\_id}, \text{full\_name}, \dots\}$
- **Evaluation:** 3NF / BCNF satisfied.

#### Table 2: `customer_profiles`
- **Candidate Keys:**
  - $CK_1 = \{\text{customer\_id}\}$ (Primary Key)
  - $CK_2 = \{\text{user\_id}\}$
- **Foreign Keys:**
  - $\text{user\_id} \rightarrow \text{users(user\_id)}$
- **Functional Dependencies:**
  - $\text{customer\_id} \rightarrow \{\text{user\_id}, \text{date\_of\_birth}, \text{gender}, \text{profile\_image}, \text{created\_at}, \text{updated\_at}\}$
  - $\text{user\_id} \rightarrow \{\text{customer\_id}, \text{date\_of\_birth}, \dots\}$
- **Evaluation:** 3NF / BCNF satisfied.

#### Table 3: `provider_profiles`
- **Candidate Keys:**
  - $CK_1 = \{\text{provider\_id}\}$ (Primary Key)
  - $CK_2 = \{\text{user\_id}\}$
- **Foreign Keys:**
  - $\text{user\_id} \rightarrow \text{users(user\_id)}$
- **Functional Dependencies:**
  - $\text{provider\_id} \rightarrow \{\text{user\_id}, \text{experience\_years}, \text{professional\_bio}, \text{verification\_status}, \text{average\_rating}, \text{total\_reviews}, \text{service\_city}, \text{service\_pincode}, \text{created\_at}, \text{updated\_at}\}$
- **Evaluation:** 3NF / BCNF satisfied.

#### Table 4: `categories`
- **Candidate Keys:**
  - $CK_1 = \{\text{category\_id}\}$ (Primary Key)
  - $CK_2 = \{\text{category\_name}\}$
- **Functional Dependencies:**
  - $\text{category\_id} \rightarrow \{\text{category\_name}, \text{description}, \text{category\_status}, \text{created\_at}, \text{updated\_at}\}$
- **Evaluation:** 3NF / BCNF satisfied.

#### Table 5: `services`
- **Candidate Keys:**
  - $CK_1 = \{\text{service\_id}\}$ (Primary Key)
- **Foreign Keys:**
  - $\text{provider\_id} \rightarrow \text{provider\_profiles(provider\_id)}$
  - $\text{category\_id} \rightarrow \text{categories(category\_id)}$
- **Functional Dependencies:**
  - $\text{service\_id} \rightarrow \{\text{provider\_id}, \text{category\_id}, \text{service\_name}, \text{description}, \text{price}, \text{estimated\_duration}, \text{service\_status}, \text{created\_at}, \text{updated\_at}\}$
- **Evaluation:** 3NF / BCNF satisfied.

#### Table 6: `availability_slots`
- **Candidate Keys:**
  - $CK_1 = \{\text{slot\_id}\}$ (Primary Key)
  - $CK_2 = \{\text{provider\_id}, \text{slot\_date}, \text{start\_time}, \text{end\_time}\}$
- **Foreign Keys:**
  - $\text{provider\_id} \rightarrow \text{provider\_profiles(provider\_id)}$
- **Functional Dependencies:**
  - $\text{slot\_id} \rightarrow \{\text{provider\_id}, \text{slot\_date}, \text{start\_time}, \text{end\_time}, \text{slot\_status}, \text{created\_at}, \text{updated\_at}\}$
- **Evaluation:** 3NF / BCNF satisfied.

#### Table 7: `bookings`
- **Candidate Keys:**
  - $CK_1 = \{\text{booking\_id}\}$ (Primary Key)
- **Foreign Keys:**
  - $\text{customer\_id} \rightarrow \text{customer\_profiles(customer\_id)}$
  - $\text{service\_id} \rightarrow \text{services(service\_id)}$
  - $\text{slot\_id} \rightarrow \text{availability\_slots(slot\_id)}$
- **Functional Dependencies:**
  - $\text{booking\_id} \rightarrow \{\text{customer\_id}, \text{service\_id}, \text{slot\_id}, \text{booking\_date}, \text{service\_price}, \text{booking\_status}, \text{customer\_notes}, \text{cancellation\_reason}, \text{created\_at}, \text{updated\_at}\}$
- **Evaluation:** 3NF / BCNF satisfied. Price snapshot `service_price` satisfies temporal billing integrity.

#### Table 8: `reviews`
- **Candidate Keys:**
  - $CK_1 = \{\text{review\_id}\}$ (Primary Key)
  - $CK_2 = \{\text{booking\_id}\}$
- **Foreign Keys:**
  - $\text{booking\_id} \rightarrow \text{bookings(booking\_id)}$
  - $\text{customer\_id} \rightarrow \text{customer_profiles(customer_id)}$
- **Functional Dependencies:**
  - $\text{review\_id} \rightarrow \{\text{booking\_id}, \text{customer\_id}, \text{rating}, \text{comment}, \text{created\_at}, \text{updated\_at}\}$
- **Evaluation:** 3NF / BCNF satisfied.

#### Table 9: `addresses`
- **Candidate Keys:**
  - $CK_1 = \{\text{address\_id}\}$ (Primary Key)
- **Foreign Keys:**
  - $\text{customer\_id} \rightarrow \text{customer\_profiles(customer\_id)}$
- **Functional Dependencies:**
  - $\text{address\_id} \rightarrow \{\text{customer\_id}, \text{address\_line}, \text{city}, \text{state}, \text{pincode}, \text{landmark}, \text{address\_type}, \text{is\_default}, \text{created\_at}, \text{updated\_at}\}$
- **Evaluation:** 3NF / BCNF satisfied.

#### Table 10: `admin_logs`
- **Candidate Keys:**
  - $CK_1 = \{\text{log\_id}\}$ (Primary Key)
- **Foreign Keys:**
  - $\text{admin\_id} \rightarrow \text{users(user\_id)}$
- **Functional Dependencies:**
  - $\text{log\_id} \rightarrow \{\text{admin\_id}, \text{action\_type}, \text{target\_type}, \text{target\_id}, \text{description}, \text{created\_at}\}$
- **Evaluation:** 3NF / BCNF satisfied.

### 3. Academic DBMS Demonstration Readiness Mapping

The database schema is constructed specifically to support comprehensive academic demonstration scenarios across all standard DBMS curricula:

| DBMS Category | Platform Capability / Demonstration Scenario | Relevant Schema Components |
|:---|:---|:---|
| **DDL** (Data Definition Language) | Identity columns, constraints, unique indexes, tables, drops, alters | All 10 tables, `CREATE TABLE`, `CREATE INDEX`, `ALTER TABLE` |
| **DML** (Data Manipulation Language) | Insert, update, delete across entities with cascading behaviors | `INSERT INTO bookings`, `UPDATE availability_slots`, `DELETE FROM reviews` |
| **DQL** (Data Query Language) | Complex queries with multi-table joins, aggregations, filtering | Marketplace search, customer booking history, admin metrics |
| **DCL** (Data Control Language) | Role permissions, `GRANT`, `REVOKE` for app user vs admin user | `GRANT SELECT, INSERT ON bookings TO app_user;` |
| **TCL** (Transaction Control Language)| Atomic bookings with `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT` | Slot booking reservation transaction |
| **INNER JOIN** | Matching customers with their confirmed bookings and services | `bookings INNER JOIN services ON bookings.service_id = services.service_id` |
| **LEFT JOIN** | All providers and their reviews, including unreviewed providers | `provider_profiles LEFT JOIN services ... LEFT JOIN reviews` |
| **RIGHT JOIN** | Categories and all associated services, retaining categories without services | `services RIGHT JOIN categories ON services.category_id = categories.category_id` |
| **Nested Subqueries** | Customers who booked services with price greater than average | `WHERE service_price > (SELECT AVG(price) FROM services)` |
| **Correlated Subqueries** | Providers whose average rating exceeds city-wide average rating | `WHERE average_rating > (SELECT AVG(p2.average_rating) FROM provider_profiles p2 WHERE p2.service_city = p1.service_city)` |
| **EXISTS / NOT EXISTS** | Providers with NO active bookings | `WHERE NOT EXISTS (SELECT 1 FROM services s JOIN bookings b ON s.service_id = b.service_id WHERE s.provider_id = p.provider_id AND b.booking_status = 'PENDING')` |
| **ANY / ALL** | Services priced higher than ALL services in Category X | `WHERE price > ALL (SELECT price FROM services WHERE category_id = 2)` |
| **GROUP BY & HAVING** | Categories having more than 5 registered services with avg price > 500 | `GROUP BY category_id HAVING COUNT(service_id) > 5 AND AVG(price) > 500` |
| **Aggregate Functions** | `COUNT`, `SUM`, `AVG`, `MIN`, `MAX` | Total platform revenue, average duration, rating calculations |
| **UNION / UNION ALL** | Consolidated activity timeline combining bookings and admin logs | `SELECT 'BOOKING' AS type, booking_date FROM bookings UNION ALL SELECT 'LOG', created_at FROM admin_logs` |
| **Views** | Virtualized marketplace catalog view | `CREATE VIEW v_active_marketplace AS ...` |
| **Triggers & Stored Procedures**| Automated rating updates, slot status sync, review eligibility | `trg_validate_booking_integrity`, `trg_sync_slot_status`, `trg_update_provider_ratings` |
| **Transactions & Concurrency** | Pessimistic locking to eliminate booking collision race conditions | `SELECT * FROM availability_slots WHERE slot_id = $1 FOR UPDATE;` |
